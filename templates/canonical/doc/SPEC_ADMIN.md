# SPEC_ADMIN

Generic ops-admin UI. One shell, schema-driven, serves every resource that opts in via Primer. Django-admin-equivalent, fully typed.

## Scope

**In scope:** ops-admin — the dev/staff UI for inspecting, creating, editing, deleting records. One aesthetic, no knobs, mounted at `/admin`.

**Out of scope:** customer-facing admin panels (product features like "tenant admin manages their org users"). Those are user-owned Vue pages that consume the generated composables like any other product page.

Admin behavior for a resource (field visibility, widget overrides, labels, action buttons) is declared in the resource's state file at `storage/blast/state/resources/<name>.ron` or the app-level state file at `storage/blast/state/app.ron`.

## Shell Shape

One set of generic SFCs + a runtime registry. All generated by Blast:

```
frontend/src/generated/admin/
├── AdminShell.vue        (sidebar + router-outlet; user mounts at /admin)
├── AdminList.vue         (generic DataTable for any resource)
├── AdminForm.vue         (generic form; reads widget registry)
├── AdminDetail.vue       (read-only record view)
├── registry.ts           (typed map: resource → columns/widgets/labels/composables)
└── widgets/
    ├── TextWidget.vue
    ├── TextareaWidget.vue
    ├── NumberWidget.vue
    ├── BoolWidget.vue
    ├── DateTimeWidget.vue
    ├── EnumSelectWidget.vue
    ├── FkLookupWidget.vue
    ├── JsonEditorWidget.vue
    └── MarkdownWidget.vue
```

User mounts once:

```vue

<script setup lang="ts">
import AdminShell from '@/generated/admin/AdminShell.vue';
</script>
<template><AdminShell /></template>
```

Router entry: `{ path: '/admin', component: () => import('@/AdminEntry.vue') }`.

## Widget Inference (schema.rs types → default widgets)

| Diesel type | Default widget |
|-------------|---------------|
| `Text`, `Varchar(n)` (n ≤ 200) | `TextWidget` |
| `Varchar(n)` (n > 200) or long-text | `TextareaWidget` |
| `Int2/4/8`, `Float4/8`, `Numeric` | `NumberWidget` |
| `Bool` | `BoolWidget` (toggle) |
| `Timestamp`, `Timestamptz`, `Date`, `Time` | `DateTimeWidget` |
| `Uuid` | `TextWidget` (readonly for `id` by convention) |
| `Jsonb` + `typed_as::<T>()` | `JsonEditorWidget` (typed) |
| `Jsonb` (untyped) | `JsonEditorWidget` (raw) |
| FK column | `FkLookupWidget` (async dropdown against target resource list API) |
| `DbEnum`-backed | `EnumSelectWidget` |

Primer can override per field via `admin_hints`.

## Admin Hints (in resource state file)

Declared per resource in `storage/blast/state/resources/<name>.ron`. All optional. Sensible defaults inferred from `schema.rs` types and field variant membership.

Example fields in the state file:

```ron
admin_hints: Some(AdminHints(
    columns: ["email", "role", "created_at"],
    widget_overrides: { "description": Markdown, "settings": JsonEditor },
    labels: { "email": "Email Address" },
    searchable: ["email", "name"],
    default_sort: ("created_at", Desc),
    hidden_actions: [Delete],
))
```

Blast reads these at `blast gen all` time and emits the admin registry accordingly.

## Registry Emission

Blast emits `registry.ts`:

```ts
import { useAdminUsers, useAdminUser, useAdminUpdateUser, useAdminDeleteUser } from '../composables/admin/users';


export const adminResources: AdminResourceEntry[] = [
  {
    name: "users",
    label: "Users",
    listEndpoint: "/api/admin/users",
    detailEndpoint: (id) => `/api/admin/users/${id}`,
    columns: [  ],
    widgets: { email: "TextWidget", description: "MarkdownWidget",  },
    labels: { email: "Email Address" },
    searchable: ["email", "name"],
    defaultSort: { field: "created_at", dir: "desc" },
    composables: { list: useAdminUsers, get: useAdminUser, update: useAdminUpdateUser, delete: useAdminDeleteUser },
    hiddenActions: ["Delete"]
  }
  
];
```

Typed imports; tree-shaken at build.

## Inclusion Criteria

A resource appears in admin shell if ANY of:
- Any field in the resource state file has the `Admin` variant
- Any flow in the resource state file has `auth: AdminOnly`
- `admin_hints` is declared in the resource state file

No opt-out knob beyond not declaring admin-related things in the state file.

## Admin Flows (API layer)

Blast emits admin-specific flow scaffolds under the standard layer chain (`transport → flow → routine → {models, services} → database`):

```
src/flows/generated/admin/<resource>/list.rs
src/flows/generated/admin/<resource>/get.rs
src/flows/generated/admin/<resource>/update.rs
src/flows/generated/admin/<resource>/delete.rs
```

Each flow opens with `ctx.require_role(Role::Admin)?` and declares a `Crank` retry policy. Flows call routines; routines call models and services. Transport handlers call flows only — no layer skipping. These flows use the `Admin` response variant (more fields than `Public`). Routes mount under `/api/admin/<resource>`.

## Customization Escape Hatch

For admin actions that aren't generic CRUD (e.g. "rerun failed job", "issue refund"):

```vue

<script setup lang="ts">
import { useAdminRefundOrder } from '@/generated/composables/admin/orders';
import { Button } from 'primevue';
const props = defineProps<{ row: OrderAdmin }>();
const refund = useAdminRefundOrder();
</script>
<template>
  <Button label="Issue Refund" @click="refund(props.row.id)" />
</template>
```

Custom admin actions are declared in `storage/blast/state/app.ron`:

```ron
admin_actions: [
    AdminAction(
        resource: "orders",
        label: "Issue Refund",
        component: "admin/actions/OrderActions.vue",
        flow: "admin::orders::refund",
    ),
]
```

Shell renders the custom action component alongside the generic form on that resource's detail view.

Heavy customization (wildly different admin view per-resource) = fork the shell or opt out of admin for that resource and build product-side.

## No Design Knobs

- One admin aesthetic (PrimeVue Lara + app tokens)
- Fixed sidebar layout, fixed DataTable layout, fixed form layout
- Restyling = fork the shell (small code, all in generated/admin/)
- Consistent with "opinionated defaults, fork if you want different"

## Auth Note

FE admin route gate (`/admin`) is cosmetic. API enforces at the flow level — every admin flow calls `ctx.require_role(Role::Admin)?` as its first statement. Session must carry the admin role; the flow rejects the request before any work is done. FE hides what the API would refuse anyway.
